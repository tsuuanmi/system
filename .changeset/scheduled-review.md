A scheduled review of existing code, one area a day, filing what it confirms as proposed board tasks (T290, D93 item 8, after Anthropic's "Solving code review"):
- **One area a day, round robin, off by default.** `workflow.scheduledReview` (`enabled` false until the operator sets it, with `projectId` and `repository`; `ref` default `dev`, `hourUtc` 3, `maxTasksPerRun` 5, bounds on the files and bytes read, `timeoutMinutes`) reviews the day's area: the repository's `docs/review/*.REVIEW.md` guides, read at the tip of `ref`, in name order, the UTC day number modulo their count. At most one scheduled review a day; `scheduledReviewNow` runs one outside the schedule. A setting out of range, or `enabled` without a project and repository, refuses the row at load and in `system check`.
- **The whole area at the tip, not a diff.** The files matching the guide's `paths`, each line numbered, with the guide's text, to the new `scheduled-review` template (`profile-software-development`): `review:1` at the frontier tier reports `important` findings and nits; `verify:1`, a second reviewer that prefers another provider family, votes with a reason on each important finding; its votes count only when it ran on another family than `review:1` (else nothing is filed, and the row says why). An area that does not fit is read as consecutive windows around the ring of its files, each round starting where the last ended, so every file is read within as many rounds as the area has files; the files left are named and counted.
- **A restart never loses a review.** Its run is on its row from the moment it is admitted; a review the host stopped is settled from that run at the next start (and every pass), its tasks written to the row one by one so none is proposed twice; one cut before its run was admitted is recorded failed, with why.
- **A confirmed important finding is one proposed board task** with its `file:line`, evidence, the verifier's reason, and the guide it broke. A finding the verifier rejected or did not vote on, or whose file and line the reviewers were not shown, is never filed. At most `maxTasksPerRun` tasks a run, the rest counted as capped. A finding is not filed while a task for it is open: the same file and title, the same file within three lines, or any open task of the project with the same title.
- **The report counts per area over time.** A new `workflow_scheduled_reviews` table (store migration 25) keeps each review's area, commit, and counts (important, confirmed, rejected, unverified, nits, filed, duplicates, capped); `scheduledReviewReport()` sums them per area and lists the latest reviews, unfinished ones included, with why.

Docs: [the handbook](../docs/design/handbook.md#scheduled-review), [workflow templates](../docs/reference/workflow-templates.md#scheduled-review), [configuration](../docs/reference/configuration.md#workflow). **Behaviour change:** none while `scheduledReview.enabled` is unset; the profile row now also provides the `scheduled-review` template.
