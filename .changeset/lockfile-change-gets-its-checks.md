A task that changes the lockfile gets its checks: the supply-chain verification of a new lockfile runs once, online, on an approval (T333; seen on T328; D112):
- A setup run again for a result's checks that is refused `dependency_unavailable` for only the lockfile's verification (`ERR_PNPM_NO_OFFLINE_META` alone, no missing tarball) opens one approval request (class `command`) per lockfile digest, for the exact argv of the verification (the setup's install, only when it is pnpm's own frozen install — `pnpm`/`corepack pnpm install --frozen-lockfile` with known options, never a script — without `--offline`, with `--ignore-scripts --ignore-pnpmfile`), its subject the exact execution (digest, argv, registry, cache, deadline), so an approval runs only what it names, and every held result with that lockfile, in any worktree, shares that one request, naming the registry and that the host's network is shared while it runs. The result's `.npmrc`, `pnpm-workspace.yaml`, and lockfile are read against allowlists (layout settings only, no registry but this one, every resolution a registry package's or a local directory's), so a setting in any spelling the scan does not know refuses it: such a result is not asked about, and its checks stay not run, naming each finding. New `worktreeSetup[].lockfileVerification` (`registry`, `cacheDir`, outside every path hidden from agents; every setup run of the repository sees `cacheDir` read-only) and ledger table `agent_lockfile_verifications` (agent-workers store migration 24).
- Approved, the host runs it once, confined, sharing the host's network for that command only (a confinement cannot limit it to one host), none of the result's code run, the registry named in its environment and corepack forbidden to download, writing only the worktree and pnpm's metadata cache; the outcome is a `gate` decision (rule `agent-workers.lockfile-verification`); the setup and then the result's checks run again by themselves (`Checked` refusals carry the `requests` they wait on; a held result's landing watch asks again once none is open). Rejected or expired, the checks stay not run, naming the request. A digest verified is never asked again.
- The new `lockfile-verification` mechanism (`off`, `warn`, `on`; configured by `enforce.lockfileVerification`, starts `warn`: it records, once per digest, the request it would open and opens none). Mechanisms may now declare a start mode (`Mechanism.start`).
